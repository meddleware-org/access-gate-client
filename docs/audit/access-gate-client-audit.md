## Executive summary

The package is 1,879 lines of source across 10 modules, with no runtime dependency (`@mysten/sui` is a
peer since 0.0.6). It is the single place where `access_gate` objects are read, events decoded and PTBs
built.

Its core discipline is strong and well tested:

- **Exact types.** Normalised full-type matching at the original id, with look-alike-package tests
  for objects and events.
- **No truncation.** Owned-object reads page to the end and throw past 100 pages.
- **Fail-closed parsers.** Object parsers use strict readers and return `null` on any missing
  or mistyped field. The pass variant is a discriminated value and an unparsable one rejects the
  object (0.0.5).
- **Normalised IDs.**
- **Safe amounts and addresses.** u64 amounts go through `toU64`, which refuses unsafe numbers.
  Recipients must be full 64-hex addresses; the nonce must be at least 8 bytes.
- **Exact, strict BCS events.** Events decode from BCS, re-serialise to the same bytes (trailing
  bytes refuse), with a prototype-key guard.
- **Location-scoped aborts.** An abort is only claimed when it is located in `access_gate` of the given
  original id. The table covers codes 1-14 (15 and 16 are missing: F24).
- **Generated IDs.** Deployment IDs are generated from the published Move records and drift-checked
  in CI.
- **Builder tests.** Every builder's target and **exact argument order** is asserted hermetically.
  A weekly live suite compares each builder's Move function with the chain, down to the reference
  kind and type per parameter, and compares every struct the parsers read.

At the 2026-10-09 re-verification: **145/145 unit tests pass** (8 files); 98.37% statements, 95.2%
branches, 100% functions, 99.52% lines; tsc, eslint, `npm audit` (0) and `check:deployments` are clean;
the live read-only suite passes against the 2026-10-09 testnet package (47 passed, 3 skipped).

**Where the risk concentrates (2026-10-09).** Every finding of the 2026-10-03 baseline is closed by
0.0.5-0.0.8 (see the re-verification log):

1. **F1 and F2 (Medium at baseline, now RESOLVED).** `usesRemaining: null` is replaced by a
   discriminated `variant`; an unparsable pass is rejected; `ownsAccessNft` counts only usable passes
   (decision: ownership counts usable passes only). The Worker's call site (`chain.ts::ownsNftLive`)
   inherits the usable-only default through client 0.0.6; the gateway audits track their own F7
   dispositions (gateway-rust implements the same rule natively and is undeployed).
2. **Drift coverage (F3, F4, RESOLVED).** Strict event decode, a schema comparison for every struct
   the parsers read, per-parameter ABI checks and a weekly live job.
3. **Hardening (F5-F13, RESOLVED).** Prototype-key lookup, `locked_commission`, indexer bounds and bad
   rows, the peer dependency, builder input checks, commission helpers, bounded gate reads, abort
   scoping.
4. **Remaining: F24 (Low).** The abort table stops at code 14 while the 2026-10-09 package adds
   `E_POLICY_COMBINATION` (15) and `E_USES_KIND_IMMUTABLE` (16), and one `AGENTS.md` row is stale. This
   is a maintainer patch item (next release 0.0.9), not mainnet-blocked.

Mainnet remains unpublished, so the pre-mainnet gates that need a mainnet record or an external review
stay open in Section D.

## Findings

### F1 — `usesRemaining: null` conflates "unlimited pass" with "count unknown"; the enum JSON shape is unpinned

**Severity:** Medium   **Disposition:** RESOLVED (0.0.5, `8435927`; OQ1 decided: option (a))
**Where:**

- `src/ownership.ts:51-62` (`parseUsesRemaining`) and `:69-73`
- `src/types.ts:113-119` (`usesRemaining: number | null` — "`null` for an unlimited pass")
- `tests/ownership.test.ts:31-34, 83-116`

**Issue:**

- `parseUsesRemaining` returns `null`, the documented value for an **unlimited pass**, in three cases:
  - the tag is `UnlimitedPass`;
  - the tag is unrecognised;
  - a `SingleUse` count is missing or malformed ("never a fabricated 0").
- The tag is looked up as `v.variant ?? v.type ?? v.$kind`, and the fixtures use
  `{ variant: 'SingleUse', fields: { uses_remaining } }`. No live test asserts how the full node
  actually renders a Move enum in object `json`.
  - If the real rendering uses another key (for example `@variant`), the code still returns the
    count, but only because `uses_remaining` happens to be present. The comment says the opposite
    ("driven by the enum variant tag … rather than guessing from field presence").
  - A rendering that nests or renames the count turns every single-use pass into "unlimited".
- Unlike every other parser in the package, this one does not fail closed.

**Impact:** consumers already treat `null` as unlimited.

- walrus-relay `useAccessGate.ts:92` keeps `usesRemaining === null` passes as usable and sorts them
  last.
- token-deployer-ui `IconPicker.vue:165` sets `singleUse: usesRemaining !== null`, so an unknown count
  skips the on-chain consume, and the single-use gateway then rejects the upload with no clear cause.
- Once nft-gate F7 adds a uses check to `ownsAccessNft` (F2), an unknown count would **admit** an
  exhausted pass.

**Remediation / evidence (2026-10-09):** `OwnedAccessNft.usesRemaining` is replaced by `variant: PassVariant`, a discriminated
`{ kind: 'unlimited' } | { kind: 'singleUse', remaining: bigint }` (exact u64). `ownership.ts::parseVariant`
reads the rendering a full node returns (`@variant`) and returns `null` for an unknown or missing tag or a
count that is not a u64; `parseOwnedAccessNft` then returns `null`, so the pass is absent from
`fetchAccessNfts` and never counts as access. The comment is corrected. Tests: `pass variant fails closed ›
rejects every variant it cannot parse instead of reading it as unlimited`, `keeps u64 counts exact,
including the maximum`. The real rendering is pinned by `tests/integration/grpc-read.integration.test.ts`
(`fetchAccessNftById` on a real testnet single-use pass, asserting `variant.kind` and a `bigint` count;
passing on 2026-10-09). Consumers moved in step: walrus-relay `useAccessGate.ts` filters with
`isUsablePass` and carries the `variant`; token-deployer-ui reads `accessGate.singleUse` and no longer
sees a nullable count. Unlimited-vs-unknown can no longer be confused.

**Baseline recommendation (2026-10-03):**

- Return a discriminated value: `variant: { kind: 'unlimited' } | { kind: 'singleUse', remaining:
  bigint }`.
- Make `parseOwnedAccessNft` return `null` (reject the object) when the variant cannot be parsed.
- Keep u64 as `bigint` (SC lens §A *Value encoding*) instead of a saturating `number`.
- Pin the real rendering with a live integration assertion on a known unlimited pass and a known
  single-use pass, both in testnet fixtures.
- Correct the comment.
- Update walrus-relay and token-deployer-ui in the same release (pre-v0.2: no compatibility shim
  needed).

### F2 — `ownsAccessNft` is used to authorise but admits exhausted single-use passes

**Severity:** Medium   **Disposition:** RESOLVED (0.0.5, `8435927`; OQ2 decided: usable-only by default in `ownsAccessNft`)
**Where:** `src/ownership.ts:133-146`; consumer `nft-gate/gateway-workers/src/chain.ts::ownsNftLive`.

**Issue:**

- `ownsAccessNft(client, owner, nftType, gateId)` is true for any owned pass of the gate, including a
  `SingleUse { uses_remaining: 0 }` receipt. Gates with `auto_burn_at_zero = false` keep these by
  design.
- The package's own docs frame its reads as display helpers. `SECURITY.md` invariant 3 is about the
  indexer, but the README presents `ownsAccessNft` as a convenience.
- The Workers gateway uses this function as its ownership-mode authorisation decision.
- `seal_policies::nft_gate`, the other on-chain consumer of passes, rejects exhausted passes.

**Impact:** In ownership mode, holders of spent passes keep unlimited access. This is latent, because
the live relay runs single-use mode.

**Remediation / evidence (2026-10-09):** `ownsAccessNft(client, owner, nftType, gateId?, { usable })` counts only usable passes by default
(unlimited, or single-use with `remaining > 0`); `{ usable: false }` counts every pass of the type. A pass
whose variant cannot be parsed never counts. Tests: `owned-object reads › ownsAccessNft counts usable
passes only by default`, `ownsAccessNft never counts a pass whose variant is unknown`, `isUsablePass ›
counts unlimited and non-empty single-use passes only`. `SECURITY.md` invariant 3 and `CLAUDE.md`
("Authorisation role") now document the function as authorisation-grade. The nft-gate Worker's call site
(`gateway-workers/src/chain.ts::ownsNftLive`) inherits the default; the Worker resolves client 0.0.6,
which includes this change. The gateway audits track their own F7 dispositions.

**Baseline recommendation (2026-10-03):**

- Give the function an explicit, fail-closed semantics. For example, `ownsAccessNft(…, { usable:
  true })` (default `true`) counts only unlimited passes and single-use passes with `remaining > 0`,
  and depends on F1.
- Document it as authorisation-grade in `SECURITY.md`.
- Add tests: an exhausted pass is not counted, and an unknown variant is not counted.
- Bump nft-gate to the new patch.

### F3 — No drift test for event layouts or object field names against the chain

**Severity:** Low   **Disposition:** RESOLVED (0.0.6 `f7d3f15` strict decode; 0.0.7 `a8e5f16` schema drift suite)
**Where:** `src/events.ts:17-81` (BCS layouts "mirror the Move structs field for field");
`src/gates.ts:37-99`, `src/ownership.ts:82-91` (JSON field names); `tests/integration/abi-drift.integration.test.ts`
(functions only).

**Issue:** The ABI-drift test compares builder targets and arity with the on-chain functions. Nothing
compares the eight event structs, or the object structs the parsers read (`Gate`, `PlatformConfig`,
`AdminCap`, `AccessData`, `AccessVariant`, `CommissionTerms`, `GatePolicy`), with the package's
normalised datatypes.

`@mysten/bcs` `parse` does not reject trailing bytes:

- a field appended to an event in a future upgrade or republish decodes silently and is lost;
- a field inserted mid-struct produces wrong values without an error, unless a length check happens
  to fail.

The hermetic event tests encode with the same layouts they decode, so they cannot detect drift (SC
lens §C: "a test that only compares a hand-built vector with itself proves nothing").

**Impact:** After an `access_gate` change, the treasury/dao activity feeds and `consumer`/`nonce`
displays could show wrong data without any failing test. The gateways do not use these decoders.

**Remediation / evidence (2026-10-09):** `events.ts::parseAccessGateEvent` now decodes strictly: it re-serialises the parsed value and
throws unless the bytes are identical, so a trailing field from an upgrade or a mismatched layout no longer
decodes silently (test `rejects trailing bytes: a field appended by a later upgrade must not decode
silently`). `tests/schema.ts` records the exact fields (name, order, Move type) of every struct the parsers
read; `tests/schema.test.ts` encodes values from that schema with an encoder independent of
`src/events.ts` and checks they round-trip through the real parsers, trailing bytes included.
`tests/integration/schema-drift.integration.test.ts` compares each recorded struct with
`getDatatype` on the live package and decodes a real event of each kind strictly (skipped per kind when the
full node has pruned them). Passing against the 2026-10-09 package.

**Baseline recommendation (2026-10-03):**

- In the integration suite, fetch each datatype from `publishedAt`, using the core API or
  `MovePackageService.getDatatype`.
- Compare field names, order and types with each `LAYOUTS` entry, and with the JSON field names the
  parsers read.
- Also decode one real event of each kind and fail if bytes remain.

### F4 — ABI drift compares arity only and never runs in CI

**Severity:** Low   **Disposition:** RESOLVED (0.0.6 weekly job; 0.0.7 `a8e5f16` per-parameter types)
**Where:** `tests/integration/abi-drift.integration.test.ts:24-37` (visibility, type-parameter count,
parameter count); `.github/workflows/node-ci.yml` (no integration job).

**Issue:**

- The drift check would not catch a reordering or a type change between parameters of the same
  count. Examples:
  - `(cap, gate, platform, value)` becoming `(cap, platform, gate, value)`;
  - `u64` becoming `u128`;
  - `&Gate` becoming `&mut Gate`.

  The hermetic "exact arguments" tests (`tests/ptb.test.ts:219-298`) pin the order against expectations
  written by hand, not against the chain.
- The live suite is manual (`GRPC_TESTNET=1`), and no run is recorded in the repo. The TS lens says
  every test project should run in CI; the SC lens's pre-testnet gate needs the drift test green with
  evidence.

**Impact:** ABI drift after an `access_gate` republish would surface only when a user's transaction
fails.

**Remediation / evidence (2026-10-09):** `tests/abi-table.ts::EXPECTED_PARAMS` records the reference kind and type per parameter of every
Move function a builder calls; `abi-drift.integration.test.ts` compares each with the live function
(`paramType`), so a reorder or a `u64` to `u128` / `&` to `&mut` change fails, not only an arity change.
The completeness test `tests/abi-table.test.ts` forces every exported builder into the table, and an

### F7 — `readIndexerEvents`: bounds, redirects and path resolution

**Severity:** Low   **Disposition:** RESOLVED (0.0.6, `f7d3f15`)
**Where:** `src/events.ts:378-408`.

**Issue:**

- **(a) Body read unbounded.** `res.text()` reads the whole body before the 1 MiB check, and
  `text.length` counts UTF-16 units, not bytes.
- **(b) Redirects followed.** `fetch` uses the default `redirect: 'follow'`, so an https indexer can
  redirect to `http:` in Node or workerd, and the https check applies to the configured base only.
- **(c) `path` can escape the check.** `new URL(path, base)` lets an absolute or protocol-relative
  `path` (`//evil.example/…`, `https://evil/…`) leave the checked host. The function is exported and
  shared with seal-client, which passes a constant today.

**Impact:** Display data only; nothing authorises on it. The risks are a client-side memory spike, a
plaintext downgrade, or a future caller reading from an unchecked host.

**Remediation / evidence (2026-10-09):** All three parts are fixed in `events.ts::readIndexerEvents`: (a) `readCappedText` rejects on
`Content-Length` and counts bytes while streaming, cancelling the reader past 1 MiB; (b) `fetch` uses
`redirect: 'error'` and `cache: 'no-store'`; (c) `path` must be relative (no scheme, no leading `/`, no
backslash) and `url.origin` must equal the indexer's origin. Tests: `caps the body by bytes while streaming,
even without a Content-Length`, `refuses a path that leaves the indexer origin, and redirects`,
`rejects oversized, non-JSON and mis-shaped bodies`.

**Baseline recommendation (2026-10-03):**

- Cap via `Content-Length` and a streamed byte counter.
- Use `redirect: 'error'` and `cache: 'no-store'`.
- Require `path` to be relative (no scheme, no leading `//`) and check `url.origin === base.origin`.
- Add tests for each.

### F9 — `@mysten/sui` is a runtime dependency, not a peer

**Severity:** Info   **Disposition:** RESOLVED (0.0.6, `f7d3f15`; OQ3 decided: peer dependency)
**Where:** `package.json` `dependencies: { "@mysten/sui": "^2.33.1" }`; `src/ptb.ts:1` (`new Transaction()`).

**Issue:**

- The builders return `Transaction` instances created from this package's copy of `@mysten/sui`.
- Hosts sign them through wallet-adapter (`@mysten/sui` peer `^2.33.1`) with their own copy.
- A second copy in a host tree produces `#private`-mismatch type errors and can break `instanceof`
  checks. The dashboard's `CLAUDE.md` documents exactly this failure.
- Today every consumer range admits the dashboard's pin `2.33.2`, so npm dedupes.
- seal-client and wallet-adapter declare `@mysten/sui` as a peer, which is the pattern that guarantees
  one copy.

**Impact:** A future range divergence silently installs two copies in a host.

**Remediation / evidence (2026-10-09):** `@mysten/sui` is a `peerDependency` (`^2.33.2`) and a devDependency (`^2.35.0`), matching
seal-client and wallet-adapter, so a host supplies the single copy that the builders' `Transaction`
instances come from. CI runs `npm ls --all` (peer ranges satisfied); this repo has no `legacy-peer-deps`.
The shared-dependency matrix row in B.1 is updated.

**Baseline recommendation (2026-10-03):** Move `@mysten/sui` to `peerDependencies` (`^2.33.1`), plus a matching
devDependency. Record it in the ADR-0001 shared-dependency matrix.

### F10 — Builder input checks that would avoid failed wallet prompts

**Severity:** Info   **Disposition:** RESOLVED (0.0.7, `a8e5f16`)
**Where:** `src/ptb.ts:85-98` (`buildConsumeTx`); `src/types.ts:7-22` (`AccessGateConfig.soulbound?`
independent of `nftType`).

**Issue:**

- `buildConsumeTx` does not check that the nonce is at least 8 bytes. The contract aborts with
  `E_INVALID_NONCE` (8), but only after the user has signed and paid gas.
- `soulbound` is optional and is not derived from `nftType`, so a config with a soulbound `nftType` and
  `soulbound` unset builds `consume` (transferable), which aborts on-chain.

**Impact:** Wasted signatures and gas, and confusing errors. Funds are not at risk.

**Remediation / evidence (2026-10-09):** `buildConsumeTx` refuses a nonce shorter than `MIN_NONCE_BYTES` (8, UTF-8 bytes) with a

refuses a nonce the contract would reject, before any signature` and the `disagrees` assertions in
`tests/ptb.test.ts`.

**Baseline recommendation (2026-10-03):**

- Validate the nonce byte length (≥ 8; optionally ≤ a cap).
- Derive `soulbound` from `normalizeAccessNftType(nftType)`, and throw if they disagree.
- Add tests.

## Risks

- **Full-node honesty.** Every read trusts the caller's full node. A lying node can fabricate
  ownership, which the Workers gateway would act on. The client cannot bound this; the gateway's choice of
  node does.
- **Records supply chain.** Every builder's call target comes from the `@meddleware/access-gate-sui`
  npm tarball. Provenance and the exact pin bound this, but a compromised publish of that package plus
  a client release would redirect users' signatures.
- **JSON rendering changes.** Full-node `json` shapes are not a stable contract (the SDK documents
  this). BCS events are immune, but object parsers depend on field names and the `@variant` enum rendering.
  The weekly live suite catches a change, and the parsers fail closed (a pass is rejected, never defaulted)
  (F1, F3).
- **Indexer availability.** Event history before the indexer's coverage, or after full-node pruning,
  is unavailable. This affects display only.
- **Shared-SDK fragility.** One host-level `@mysten/sui` copy is now guaranteed by the peer declaration (F9); a
  host that ignores the peer warning still gets two copies.
- **Gateway lag.** The live Worker resolves client 0.0.6 and misses the 0.0.7 hardening; the repo is the
  gateway's, so the bump is theirs to schedule.
- **Unpublished mainnet.** Every id is testnet; the mainnet record, custody and review are maintainer items.
